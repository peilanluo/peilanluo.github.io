EXPLAIN命令

基础语法EXPLAIN [选项] 查询语句，可选的选项如下：

  • ANALYZE：执行查询并返回执行计划
  • VERBOSE：返回详细的执行计划
  • COSTS：返回包含成本信息的执行计划
  • BUFFERS：返回包含缓冲区信息的执行计划
  • FORMAT：指定返回的执行计划格式，可选值为JSON或XML

EXPLAIN输出结果解释

下面是一个典型的EXPLAIN输出结果：

1

Seq Scan on t1 (cost=0.00..184.00 rows=10000 width=36)

其中，Seq Scan表示顺序扫描操作，t1是表名，cost是操作的成本，rows是预计返回的行数，width是返回的行的宽度。

这里的cost=0.00..184.00：由"..“分割成两个数字，第一个数字“0.00”表示启动的成本，也就是返回第一行需要多少cost值；第二个数字“184.00”表示返回最后一行需要多少cost值。默认情况下，不同操作的cost值如下：

  • 顺序扫描一个数据块，cost值定为“1”。
  • 随机扫描一个数据块，cost值定位“4”。
  • 处理一个数据行的CPU代价，cost值定为“0.01”。
  • 处理一个索引行的CPU代价，cost值定位“0.005”。
  • 每个操作符的CPU代价为“0.0025”。

扫描的类型有以下几种

  1. 顺序扫描（Seq Scan）
  2. 索引扫描（Index Scan）
  3. 位图扫描（Bitmap Heap Scan）：也是走索引的一种方式。方法是扫描索引，把满足条件的行或块在内存中建一个位图，扫描完索引后，再根据位图到表的数据文件中把相应的数据读出来。如果走了两个索引，可以把两个索引形成的位图通过AND或OR计算合并成一个，再到表的数据文件中把数据读出来。当执行计划的结果行数很多时会走这种扫描，如非等值查询、IN子句或有多个条件都可以走不同的索引时。例子：

explain select * from issues where id > 97000;

# 结果
Bitmap Heap Scan on issues  (cost=23.96..1825.48 rows=990 width=419)
  Recheck Cond: (id > 97000)
  Heap Blocks: exact=405
  ->  Bitmap Index Scan on idx_issues_id  (cost=0.00..23.71 rows=990 width=0)
        Index Cond: (id > 97000)

在上面的扫描中，“Bitmap Index Scan”现在索引中找到符合条件的行，然后在内存中创建位图，再到表中扫描，也就是“Bitmap Heap Scan”。“Recheck Cond: (id > 97000)”表示在位图中重新检查符合条件的行，确保位图中的行是符合条件的。

上面三种扫描方式的典型应用场景如下：

  • 很小（如<5%）：会选择索引扫描，高效地读取少量数据。
  • 中等（如5%~10%）：会选择位图扫描，减少随机I/O，平衡性能。
  • 很大（如10%以上）：会选择顺序扫描，一次性读全表，比大量随机访问更高效。
  1. 条件过滤（Filter）：一般就是在WHERE子句中写的条件，如果条件的列上有索引，可能会走索引而不走过滤。
  2. 嵌套循环连接（NestLoop Join）：是在两个表做连接时最朴素的一种连接方式。在嵌套循环中，内表被外表驱动，外表返回的每一行都要在内表中检索找到与他匹配的行，因此整个查询返回的结果集不能太大（大于1万不适合），要把返回子集较小的表作为外表，而且在内表的连接字段上要有索引，否则会很慢。
  3. 散列连接（Hash Join）：优化器使用两个表中较小的表，利用连接键在内存中建立散列表，然后扫描较大的表并探测散列表，找出与散列表匹配的行。这种方式适用于较小的表可以完全放于内存中的情况。
  4. 合并连接（Merge Join）：通常情况下，散列连接的效果比合并连接要好，然而如果源数据上有索引，或者结果已经被排序过，此时执行排序合并连接不需要进行排序，效率会高于散列连接。
